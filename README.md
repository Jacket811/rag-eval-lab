# rag-eval-lab

**[在线看评估报告 →](https://jacket811.github.io/rag-eval-lab/)**　可切换任意两轮对比，不用装任何东西。

一套**中文技术文档 RAG 系统**的工程实践记录：不是又一个 RAG demo，而是「用数据决定该不该改配置」的过程。

> **方法不限领域。** 仓库里的示例题库来自麒麟操作系统文档，但工具、题型结构、评分口径与文档写法都是通用的。
> 换成 HR 政策、产品手册、客服问答，只需要重写 `questions.json`，脚本一行都不用改。
> 详见 [快速开始](#快速开始) 里的「换一个知识库」一节。

面向的场景很窄：企业内部技术文档（2682 个文本块）→ 本地小模型（8B，8GB 显存）→ 一线技术支持人员提问。

技术栈：Open WebUI + Ollama + pgvector + TEI 重排。全部本地运行，不依赖云服务。

---

## 为什么值得看

市面上 RAG 项目绝大多数止步于「跑通了」。这个仓库记录的是**跑通之后怎么判断好坏**：

- 一套 70 题的中文评估集，7 类（含 15 道「库里没有」的题、8 道同义变体）
- 8 组实测数据，其中 **5 组结论与直觉相反**
- 三套前端增强脚本，解决的是 Open WebUI 中文用户的实际痛点
- 踩过的坑，包括一次被误判成「检索不准」的容器崩溃

## 适合谁用

### 如果你遇到过这些情况

| 你的处境 | 这个仓库能给你什么 |
|---|---|
| 改了个参数，感觉好一点，但说不出好在哪 | 70 题评估集，改前改后各跑一次，用数字说话 |
| 用户说答不准，不知道是检索问题还是模型问题 | 只测检索层，能区分「资料没捞到」和「捞到了但模型没用上」 |
| 领导问准确率多少，只能凭感觉说「还不错」 | 按 7 类分层统计，能指出「哪类问题弱」而不是一个笼统的总分 |
| 想把整个知识库重写一遍，但不知道从哪下手 | 按类别定位低分题，只改那几篇文档 |
| 换模型 / 换参数，怕越改越差 | 有基线就能对比，也能判断「这次提升是不是噪声」 |

### 典型用途

1. **调参决策** —— kr、top_k、阈值、改写开关，每个改动都能量化
2. **文档验收** —— 写完一批入口文档，跑一遍看在别的题上有没有退步
3. **故障归因** —— 命中率突然掉了：文档被删了？重排挂了？阈值配错了？
4. **交付凭证** —— 给内部汇报时拿出「70 题 / 7 类 / 82.9% → 90.0%」而不是「效果不错」

### 不适合用来做什么

| 不适用 | 原因 | 该用什么 |
|---|---|---|
| 评估**答案质量**（幻觉、引用准确性） | 本仓库只测检索层，不调用生成模型 | 人工抽检，或补一层生成评估（本项目未做） |
| 结构化数据查询（数据库表、行情） | RAG 本身就不对口 | SQL / API |
| 还没搭起 RAG 的系统 | 没有可测的对象 | 先部署 Open WebUI + Ollama |
| 多轮对话质量 | 题库全是单轮提问 | 需要另建多轮测试集 |
| 大规模压测（并发、吞吐） | 这里是质量评估，不是性能测试 | locust / wrk + Prometheus |

## 实测数据

所有数字来自同一套 70 题测试集，只改一个变量。`top1` 是首条资料的重排相关度，`w3` 是前三段加权（0.5/0.3/0.2）。

### 1. 重排后送模型几段（k_reranker）

| 配置 | 平均 top1 | 前三加权 | 送入段数 |
|---|---|---|---|
| kr=6 | 76.5% | 65.7% | 6 |
| **kr=4** | **77.4%** | **66.7%** | 4 |
| kr=3 | 76.9% | 65.9% | 3 |

结论：**从 6 降到 4 有小幅提升**（噪声段减少），再降到 3 开始下降（多跳问题凑不齐资料）。

### 2. 粗召回几条（k）

| 配置 | 平均 top1 | 备注 |
|---|---|---|
| k=12 | 76.5% | — |
| k=6 | 74.1% | 单题从 0.72 崩到 0.25 |

**这是最反直觉的一条**：砍掉一半候选，平均分只掉 2.4 个点，但有一道题直接击穿——正确答案原本排在 7-12 位、靠重排拉上来的，池子一小就再也捞不到。

> 重排只能在已召回的池子里排序。池子变小，重排就失去意义。

### 3. 查询改写（多路检索）开关

| 配置 | top1 | 前三加权 | 送入段数 |
|---|---|---|---|
| 改写开启（3 路 query） | 0.749 | 0.643 | 8.3 |
| **改写关闭（单路）** | **0.833** | 0.641 | 3.3 |

关闭后 top1 涨 8.4 个点，段数降 60%，6 题答案全对。

**根因不在「改写」这个功能，在提示词**：Open WebUI 的默认改写模板是为联网搜索写的（要求 `broad`、`updated`），用在静态知识库上方向正好相反，模型会自作主张加进「Windows」「最新版本」这类污染词。

### 4. 相关度阈值

| 阈值 | 命中率 | 副作用 |
|---|---|---|
| 0（不过滤） | 94% | 寒暄也会检索并塞资料，模型被逼说「知识库中没有相关内容」 |
| **0.15** | **92%** | 能挡住寒暄，只丢 1 道边缘题 |
| 0.4 | 86% | 误杀 4 道真题（第二段补充资料分数不高但必要） |

### 5. 重排时送多少字（DOC_CHARS）

| 字数 | 结果 |
|---|---|
| 500 | 正确块排第 1 |
| 200 | **正确块跌到第 3**（答案步骤被切掉） |

重排模型的输入太短，会把「步骤列表」截断，导致真正对口的块反而不像答案。

### 6. 一个被误判的「检索故障」

某天大量回答的相关度全是 `0.01`，一开始判断为检索质量问题。查 `docker inspect` 才发现重排容器 **RestartCount=100**：

> ONNX 后端按模型配置的 `max_position_embeddings=8192` 预分配内存，24 线程直接冲到 12.8GB 被系统杀掉，陷入重启循环。

修法：把模型 `config.json` 的 `max_position_embeddings` 改成 512（实际每段只送 500 字），限制容器内存，适配器按批大小分片请求。改完 12 段重排从崩溃变成 0.6-0.9 秒。

**教训：相关度分数异常低时，先查重排服务活着没，再怀疑检索。**

## 技术选型

系统由 5 个容器组成，只有生成模型占 GPU：

| 容器 | 作用 | 跑在哪 |
|---|---|---|
| open-webui | 界面 + 切片 + 检索编排 | — |
| ollama | Qwen3-8B Q4_K_M | **GPU** |
| pgvector | 向量 + 全文索引（2682 块） | CPU |
| TEI reranker | bge-reranker-v2-m3（ONNX int8） | CPU |
| rerank-adapter | `score` → `relevance_score` 字段转换 | — |

原则：**8GB 只养得起一个模型，就只养生成模型，向量与重排全放 CPU。**

### 为什么不用 Dify

Dify 是目前最火的开源 LLM 应用平台（16 万星），不用它需要理由：

| 维度 | Dify | 这里为什么不选 |
|---|---|---|
| 编排 | 可视化拖分支、循环、多步骤 | 单轮问答链路固定，编排放不上用场 |
| 观测 | 中间值在节点日志里，隔一层 | 调参要直接看到「召回几段、重排多少分、prompt 原文」 |
| 部署 | 官方 compose 定义 47 个服务，默认起 18 个 | 单机笔记本，5 个容器 `docker ps` 一眼看完 |
| 定位 | 把多步骤拼成一个产品 | 问题是「几段最合适、阈值设多少」，属效果测量 |

反过来，如果需求是「查工单 → 判断保修 → 检索文档 → 生成草稿」这类带分支的工作流，Open WebUI 做不了，应该直接上 Dify。

完整论证见长文《[8GB 显存跑 8B 模型 + RAG](articles/8gb-vram-rag-notes.md)》的「四个决定」一节。

## 组件

### `eval/` — 检索层评估

不调用生成模型，只测「资料找得对不对」，70 题约 3-5 分钟。

```bash
python run_eval.py --validate        # 校验题库要点是否真的在库里
python run_eval.py --run --tag xxx   # 跑一轮并打标签
python run_eval.py --diff a.csv b.csv
python snapshot.py                   # 查看当前配置快照
python report.py                     # 生成单文件 HTML 报告
```

每轮 `--run` 会在 CSV 旁边自动写一个同名 `.meta.json`，记录当时的：

```
rag.top_k / top_k_reranker / relevance_threshold / chunk_size ...
重排地址、向量模型、分块参数、生成模型
容器镜像与重启次数、知识库块数、git commit
```

报告里直接能看到两轮的参数差异。**没有这一步，一个月后你没法解释某个分数是怎么来的**——只记得"改过别名"，不记得当时 top_k 是多少。

`report.py` 把 `results/` 下的**全部轮次**塞进一个自包含网页，页面顶部用下拉框随时切换「对比基准 / 当前」，不用重新生成、不用记文件名：

```
python report.py          # 载入全部轮次，默认对比最近两轮
python report.py --open   # 生成后自动打开浏览器
```

页面包含：KPI 对比、7 类命中率上下双条、逐题散点（对角线＝无变化）、升降最大的各 5 题、按类别筛选的明细表。

**零外部依赖**（内联 SVG，不加载任何 CDN），离线可开，也可以直接放到 GitHub Pages。

生成的报告长什么样：见 [eval/report.html](eval/report.html)（下载后用浏览器打开）

题库分四类，各 12-13 题：

| 类别 | 例子 | 考什么 |
|---|---|---|
| 口语 | 「电脑连不上网了，网卡好像没起来」 | 用户说人话时能不能命中 |
| 术语 | 「r8168-dkms 怎么卸载」 | 精确关键词 |
| 多跳 | 「系统盘满了导致软件商店打不开」 | 需要两段资料拼起来 |
| **无答案** | 「麒麟支持 Docker Swarm 吗」 | **敢不敢说没有** |

`cover` 指标只在**前 2 段**里找要点——放宽到 4 段会让「关键词碰巧出现在陪跑段」的错答案蒙混通过，实测宽松口径会让总分虚高 4 个百分点。

### `docker/` — 被评估系统的部署配置

`docker-compose.example.yml` 是 5 个容器的完整配置（Open WebUI + Ollama + pgvector + TEI 重排 + 字段转换），
`rerank-adapter/adapter.py` 是 TEI 与 Open WebUI 之间的字段名转换服务。

搭法见 **[部署说明](docs/deploy.md)**。这套容器**不是本项目的运行依赖**——它们是评估的对象。

### `obs/` — 运行状态快照

只读采集 13 项指标追加到 CSV：回答数、无资料占比、空回答、命中率中位/p10、prompt 长度分布、生成速度、容器重启次数、库体积。

```bash
python observe.py            # 采集一次
python observe.py --report   # 只看趋势
python observe.py --watch    # 采集后立刻出表
```

**它和评估集不能互相替代**：评估集测「能力」（答得对不对，可控可复现），观测测「状态」（今天慢不慢、崩没崩）。

### `theme/` — Open WebUI 前端增强

三个独立脚本，通过 `index.html` 注入，不修改后端。

| 脚本 | 作用 | 解决什么问题 |
|---|---|---|
| `hitrate.js` | 每条回答下方显示「命中率 X% \| 引用 n/m」 | 让检索质量可见，不用手动查库 |
| `ctxmeter.js` | 输入框右侧环形指示器 + 明细弹窗 | 上下文快满时能提前换会话，而不是等答案变差 |
| `ttft.js` | 等待期状态条 + 完成后显示首字/全文耗时 | 单卡串行推理时，几十秒的空白期完全没反馈 |

三个脚本都只依赖 Open WebUI 已有的接口（`/api/v1/chats/{id}`），不引入新依赖。

**`hitrate.js` 的判据**：数据来自回答消息里的 `sources[].distances`（重排分数）。注意数组**不是有序的**，取前 N 段前要先排序；只有 1 段时不能用「最高分减最低分」判断可靠性（恒为 0）。

### `docs-template/` — 文档写法示例

5 篇「入口文档」，演示怎么把口语问题对上术语文档。同一个问题、同一段内容，只改写法：

| 版本 | 向量相似度 | 重排分数 |
|---|---|---|
| 原文档（内部命名标题） | 0.6324 | 0.2950 |
| 改写版（标题用问法 + 结论先行 + 别名行） | 0.7521 | **0.9396** |
| 无关文档（对照） | 0.4962 | 0.0275 |

要点：标题写用户会说的话、结论放在第一句、别名单独一行、命令原样独立成行、一篇只讲一个问题。

## 快速开始

前提：Docker 环境，已跑起 Open WebUI + Ollama + pgvector（+ 可选的 TEI 重排）。

> **这些容器怎么搭？** 见 **[部署说明](docs/deploy.md)**——包含 5 个容器的 compose、模型拉取、
> 重排模型准备（最容易卡住的一步）、知识库创建，以及「为什么改了环境变量不生效」。
> 已经有能跑的 Open WebUI 知识库，可以直接跳过。

```bash
# 1. 评估：先按自己的环境改顶部常量，或用环境变量覆盖
cd eval
export OWUI_BASE=http://127.0.0.1:3000
export OWUI_CONTAINER=open-webui
export PG_CONTAINER=pgvector PG_USER=owui PG_DB=openwebui
python run_eval.py --validate

# 2. 在 questions.json 里把 meta.collection 改成你的知识库集合名
python run_eval.py --run --tag my-baseline

# 3. 观测
cd ../obs
python observe.py --watch

# 4. 前端脚本：把 theme/*.js 挂到 Open WebUI 的静态目录，
#    并在 index.html 里注入 <script defer src="/static/theme/xxx.js">
```

> 题库里的问题需要配你自己的文档。`--validate` 会告诉你哪些「要点」在库里找不到，据此替换。

### 换一个知识库

工具层完全不用改，只重做内容层：

```
1. questions.json 的 meta.collection → 你的集合名
2. 重写题目：结构照搬 7 类（口语/术语/多跳/精确型/同义变体/带条件/无答案），
   内容换成你的领域
3. 跑 --validate，把要点不在库里的题换词或替换掉
```

**哪些结论能直接搬，哪些必须重测：**

| ✅ 能直接搬（机制类） | ⚠️ 必须重测（数值类） |
|---|---|
| 换个说法就掉队，加别名能救回来 | `rag.top_k` 该设多少（跟库规模有关） |
| 标题写用户问法、结论先行、一篇一问 | 相关度阈值（跟分数分布有关） |
| 召回要宽、喂料要精（k 不能小，kr 可以小） | 送重排的字数（跟块长有关） |
| 小样本 A/B 会骗人（2 题 vs 6 题反转） | 查询改写值不值得开（跟提示词模板有关） |

**适用前提**（两条都满足才用得上）：

1. 知识库是**自然语言文档**，不是结构化表格
2. 用户会**用口语提问**，不是用精确的字段名/ID

反例：数据库表结构查询、行情数据查询——那类应该走 SQL/API，不是 RAG。

### 7. 同义变体：换个说法，掉一半

同一批问题换一种口语问法（8 组配对），通过率从 100% 掉到 50%：

| 主题 | 原问法 | 变体问法 | 原题 top1 | 变体 top1 |
|---|---|---|---|---|
| 软件商店 | 软件商店打不开一直转圈 | **应用商店**一直转圈进不去 | 0.781 | **0.32** |
| 双系统 | 装完双系统进不去麒麟 | 开机直接进 Windows 了 | 0.953 | **0.318** |
| 分辨率 | 屏幕分辨率不对，字特别大 | 屏幕上的字特别大改不小 | 0.624 | **0.509** |
| 网卡 | 电脑连不上网了，网卡没起来 | 上不了网，ifconfig 看不到网卡 | 0.982 | 0.827 |

成功的 4 组（桌面图标 / 输入法 / 声音 / U盘）共同点：**变体里保留了文档标题中的关键词**。

**结论：检索的命中率取决于「有没有踩中文档标题里的词」，而非语义理解。**
「应用商店」和「软件商店」在人看来是同一个东西，在向量空间里差出 0.46。

这正是查询改写（query generation）原本要解决的问题——把「应用商店」翻译成「软件商店」。
本项目的取舍是**关掉改写、改用文档里写「常见说法」别名行**，因为改写会引入其他污染（见第 3 节）。

---

### 8. 只改文档别名，同义变体从 50% 提到 100%

针对第 7 节暴露的问题，不改检索、不改模型、不加查询改写，只做了两件事：

1. 在《电脑连不上网》的「常见说法」行补上 `ifconfig 看不到网卡`、`ip a 里没有网卡`
2. 新建两篇入口文档：《软件商店打不开、下载报错怎么办》《屏幕字太大改不小、开机直接进 Windows 怎么办》
   —— 标题用问法，别名行穷举用户可能说的词，再按现象分流到原文

| 主题 | 改前 | 改后 |
|---|---|---|
| 软件商店 | top1 0.32 ❌ | **0.896** ✅ |
| 分辨率 | top1 0.509 ❌ | **0.963** ✅ |
| 双系统 | top1 0.318 ❌ | **0.832** ✅ |
| 网卡 | top1 0.827 ❌（要点覆盖不足） | **0.943** ✅ |

整体：

| 指标 | 改前 | 改后 |
|---|---|---|
| 同义变体命中率 | 50.0% | **100.0%** |
| 合计命中率 | 82.9% | **90.0%** |
| 合计（剔除 flaky） | 84.1% | **91.3%** |
| 平均 top1 | 0.659 | 0.700 |
| 未通过题数 | 12 | 7 |

**这个对比是本仓库最想说明的一件事**：

> 同样想解决「用户换个说法就找不到」的问题，
> 开查询改写（3 路 LLM 生成）只换来 top1 +8.4 点，还引入 Windows 污染、多花 5000 token；
> 改文档别名（4 篇，纯文字）换来同义变体 +50 个点，零运行时开销。

**先改数据，再改引擎。** 数据改完还不行，才轮到动检索链路。

## 已知限制

- **只测检索层**，不测生成质量。幻觉率、引用准确性目前靠人工看。
- **70 题只能分辨约 14 个百分点的差异**（95% 置信）。要分辨 10 个点需要约 144 题，5 个点需要约 576 题。
  因此本项目里「kr 从 6 改到 4，top1 提升 0.9 个点」这类结论**判定为噪声**，保留该配置的理由是省 token 而非更准。
  本项目也踩过小样本的坑：2 题时得出「关闭改写明显更好」，扩到 6 题后变成打平，最后靠 70 题的分类统计才看清真相。
- `hitrate.js` 显示的是「送入模型的资料平均相关度」，不等于答案正确率。命中率高但答案错的情况真实存在。
- 单卡小显存下推理是**串行**的，并发请求只会排队。ollama 默认只有 1 个 slot。
