# 8GB 显存跑 8B 模型 + RAG：我记了一本完整的账

> 8151 MiB，这是我笔记本显卡的全部显存，也是这个项目所有决策的起点。
> 这是一份从量化到检索的实测记录，每个数字都是自己跑出来的。

## 缘起：为什么要在 8GB 上折腾

去年我想在本地跑一个能查技术文档的问答系统：8B 模型、中文知识库、数据不出网。

听起来不难，直到我把账算清楚：

```
RTX 5070 Laptop        8151 MiB
├─ Qwen3-8B (Q4_K_M)   4900 MiB   权重
├─ KV cache (8192)      589 MiB   对话记忆
├─ 计算缓冲 + CUDA       700 MiB
└─ 桌面 / 浏览器         1065 MiB   ← 这个最容易被忘掉
                        ─────────
                        7254 MiB   已用
                         897 MiB   余量
```

**只剩 900MB。** 也就是说，任何"再加一点"的想法，都得先过显存这一关。

这篇文章记录的就是后面那些取舍：量化选哪个、上下文开到多长、检索给几段、参数怎么调。每个结论都有数据，也踩过坑。

---

## 第一笔账：量化不是"越低越好"，是"刚好装得下"

8B 模型如果用 FP16，权重就是 16.4GB，八张卡都装不下。所以必须量化。

| 量化 | 8B 权重 | 我的 8GB 卡 |
|---|---|---|
| FP16 | 16.4 GB | ❌ |
| Q8_0 | 8.7 GB | ❌ 光权重就超了 |
| Q6_K | 6.6 GB | ❌ 加上 KV 和桌面就爆 |
| Q5_K_M | 5.7 GB | ⚠️ 勉强，但不敢开 8K 上下文 |
| **Q4_K_M** | **4.9 GB** | ✅ 唯一舒服的选择 |
| Q3_K_M | 3.9 GB | ⚠️ 明显变笨 |
| Q2_K | 2.9 GB | ❌ 会答非所问 |

`K_M` 是混合量化的意思：注意力层和输出层保留更多位宽，部分前馈层压得更狠。平均约 4.8 bit/参数，质量比"一刀切 Q4"好，体积差不多。

**为什么不用 Q5？** 5.7 + 0.589 + 0.7 + 1.065 = 8.05GB，卡在 8151 的边缘。桌面随便开个浏览器就溢出，一溢出就掉到 CPU——生成速度从 45 tok/s 掉到个位数。

**一个容易被忽略的点**：embedding 模型我用的是 F16，没有量化。因为它跑在 CPU 上（`num_gpu 0`），不占显存，而向量对精度敏感——量化会让相似度整体漂移，直接影响检索排序。

> 生成模型量化影响"说得准不准"，embedding 量化影响"找得对不对"。后者更致命。

## 第二笔账：KV cache 才是真正的紧箍咒

权重是固定的，KV cache 会随着上下文长度线性增长。这个必须自己算，不然永远不知道为什么"开到 16K 就变慢"。

公式（按 Qwen3-8B 的配置）：

```
每 token = 2(K和V) × 36层 × 8个KV头 × 128维 × 2字节
         = 73,728 B ≈ 72 KB

8192 token  × 72KB  ≈  590 MB
16384 token × 72KB  ≈ 1180 MB
32768 token × 72KB  ≈ 2360 MB
```

对到显存上：

| num_ctx | KV cache | 加上其他 | 剩余 | 结果 |
|---|---|---|---|---|
| 8192 | 590 MB | 7254 MB | 897 MB | ✅ 稳定 |
| 16384 | 1180 MB | 7844 MB | 307 MB | ⚠️ 一开浏览器就爆 |
| 32768 | 2360 MB | 9024 MB | -873 MB | ❌ 直接掉 CPU |

**所以 8192 不是"随便设的"，是这张卡的物理上限。**

实测生成速度 44-45 tok/s（100% GPU），一旦掉到 CPU 大概是个位数。这个断崖式下跌是判断"有没有溢出"最直接的信号。

## 第三笔账：检索给几段资料

这是我认为最反直觉的部分。

RAG 有两层"给多少"：

- `top_k = 12`：**粗召回**，从向量库里捞多少候选
- `k_reranker = 4`：**精排后**，真正送进模型几段

我一开始以为"两个都调小能省 token"，实测发现完全相反。

### 实验一：把候选池从 12 砍到 6

50 题测试集，只改这一个变量：

| 配置 | 平均 top1 | 前三段加权 |
|---|---|---|
| k=12 | 76.5% | 65.7% |
| k=6 | 74.1% | 63.0% |

平均只掉 2.4 个点，看起来"砍一半也没差多少"。

**但翻到单题，有一道直接崩了：**

```
U盘插上没反应，桌面不显示
  k=12 → top1 = 0.72  ✅
  k=6  → top1 = 0.25  ❌
```

原因是：正确答案原本排在候选池的第 7-12 位，靠重排拉上来的。池子砍到 6，它连进池子的机会都没有。

> **重排只能在已召回的池子里排序。池子变小，重排就失去意义。**

这条我记了很久：**平均分会掩盖灾难。** 看均值只掉 2 个点，实际是"大部分题没变 + 一道题废了"。

### 实验二：把送模型的段数从 6 降到 4

| 配置 | 平均 top1 | 前三段加权 | 送入段数 |
|---|---|---|---|
| kr=6 | 76.5% | 65.7% | 6 |
| **kr=4** | **77.4%** | **66.7%** | 4 |
| kr=3 | 76.9% | 65.9% | 3 |

从 6 降到 4 反而**升了**——因为少了两段噪声，模型更容易聚焦。再降到 3 开始掉，因为多跳问题（需要两段资料拼起来）凑不齐了。

**结论：召回要宽，喂料要精。** k 是网撒多大，不能小；kr 是给模型看几份，可以小。

### 一个测量陷阱

`kr=6 → kr=3` 时，如果看"6 段平均相关度"，会发现从 48.6% 涨到 61.6%，看着像涨了 13 个点。

**其实只是分母从 6 变成 3。** 分子没变好，是参与平均的数少了。

任何"减少段数"的操作，都会让平均分自动变好看。判断有没有真变好，只能看 top1 和前三段加权。

## 第四笔账：一次被误判成"检索坏了"的故障

有天我发现大量回答的相关度全是 `0.01`，第一反应是检索出问题了。

查了重排服务：

```bash
docker inspect reranker --format 'RestartCount={{.RestartCount}}'
# RestartCount=100
```

**它在崩溃重启循环里，已经 100 次了。**

原因：ONNX 后端按模型配置的 `max_position_embeddings=8192` 预分配内存，24 线程直接冲到 12.8GB 被系统杀掉。

但我每段只送 500 字（约 300 token），根本用不到 8192。

修法：

1. 把模型 `config.json` 的 `max_position_embeddings` 改成 **512**
2. 容器限内存 8G
3. 限制 `--max-batch-tokens 2048`
4. 候选项超过 8 条时分批请求

改完，12 段重排从"崩溃"变成 0.6-0.9 秒。

从 TEI 的 `/metrics` 里还能算出更细的：

```
平均重排延迟   1.09s
├─ 模型推理    0.58s  (52%)
└─ 排队+分词   0.51s  (47%)  ← 一半时间不在模型上
p50 0.95s / p90 1.86s / p99 3.9s
```

**教训：相关度分数异常低时，先查重排服务活着没，再怀疑检索策略。**

## 第五笔账：把测试集从 50 题扩到 70 题，发现了真正的问题

一开始我只有 50 题，测出来 94%，觉得挺好。

后来意识到一个问题：**这些题都是我照着文档标题写的。** 测的是我自己的表达能力，不是系统的鲁棒性。

于是加了 8 组「同义变体」——同一个问题，换个口语说法：

| 主题 | 原问法 | 换种说法 | 原题 top1 | 变体 top1 |
|---|---|---|---|---|
| 软件商店 | 软件商店打不开一直转圈 | **应用商店**一直转圈进不去 | 0.781 | **0.32** |
| 双系统 | 装完双系统进不去麒麟 | 开机直接进 Windows 了 | 0.953 | **0.318** |
| 分辨率 | 屏幕分辨率不对，字特别大 | 屏幕上的字特别大改不小 | 0.624 | **0.509** |
| 网卡 | 电脑连不上网了，网卡没起来 | 上不了网，ifconfig 看不到网卡 | 0.982 | 0.827 |

**通过率从 100% 掉到 50%。**

#### 掉队的规律非常一致

```
❌ 失败的 4 组：换掉了文档标题里的关键词
   软件商店 → 应用商店
   分辨率   → 字特别大
   双系统   → 开机直接进
   
✅ 通过的 4 组：变体里保留了原关键词
   桌面图标全没了 → 桌面上的东西全没了（"桌面"还在）
   输入法切不出来 → 打不出中文（"输入法"隐含）
```

**检索的命中率取决于"有没有踩中文档标题里的词"，而不是语义理解。**

「应用商店」和「软件商店」在人看来是同一个东西，在向量空间里差出 0.46。

## 第六笔账：最后改的是文档，不是代码

发现同义词问题后，有两条路：

**方案 A：开查询改写**（用 LLM 把用户问题改写成多个检索式）

```
3 路 query → 3 次检索 → 融合
top1 提升 8.4 个点
代价：多 5000 token、多 1.1 秒、还引入了污染
```

污染是什么？默认的改写模板是给联网搜索写的，里面要求 `broad`（宽泛）和 `updated`（最新）。用在静态知识库上，模型会自作主张：

```
问：桌面图标不见了怎么恢复
改写结果：
  - 桌面图标不见了怎么恢复
  - Windows 桌面图标丢失的解决方法      ← 库里没有 Windows
  - 如何找回 Windows 系统中消失的图标   ← 越跑越偏
```

**方案 B：在文档里加别名**

每篇入口文档加一行「常见说法」，穷举用户可能说的词：

```markdown
# 软件商店打不开、下载报错怎么办

【常见说法】应用商店、应用市场、商店打不开、装软件的地方、
           商店一直转圈、下载失败、下载没反应
```

结果：

| 主题 | 加别名前 | 加别名后 |
|---|---|---|
| 软件商店 | 0.32 ❌ | **0.896** ✅ |
| 分辨率 | 0.509 ❌ | **0.963** ✅ |
| 双系统 | 0.318 ❌ | **0.832** ✅ |
| 网卡 | 0.827 ❌ | **0.943** ✅ |

整体：

| 指标 | 改前 | 改后 |
|---|---|---|
| 同义变体命中率 | 50.0% | **100.0%** |
| 合计命中率（70 题） | 82.9% | **90.0%** |
| 未通过题数 | 12 | 7 |

**同样想解决"用户换个说法就找不到"：**

```
开查询改写：top1 +8.4 点，多花 5000 token，带来新的污染
改文档别名：同义变体 +50 点，零运行时开销，无副作用
```

差 6 倍。

> **先改数据，再改引擎。** 数据改完还不行，才轮到动检索链路。

## 完整配置清单

跑通这套（8GB 显存、8B 模型、2700 块知识库）的最终配置：

```
模型        Qwen3-8B Q4_K_M
num_ctx     8192          ← 显存上限，不是起点
num_gpu     99（全量）

rag.top_k           12      ← 粗召回，不要小
rag.top_k_reranker  4       ← 送模型，可以小
rag.relevance_threshold  0.15  ← 挡住寒暄，别设太高
查询改写            关闭     ← 用文档别名替代
重排 DOC_CHARS      500     ← 低于 400 会切掉答案步骤

生成      temperature 0.2 / top_p 0.75 / top_k 20
```

实测：首字 3 秒左右（热态），生成 44 tok/s，70 题命中率 90%。

## 给同样在 8GB 上折腾的人，六条建议

**1. 先算账，再动手**
把权重、KV cache、缓冲、桌面占用列清楚。算不清就一定会遇到"为什么突然变慢"。

**2. 量化选"刚好装下"的那一档**
不是越低越好，也不是越高越好。卡在临界点（比如 Q5）反而最糟——它会让系统在"能用"和"掉 CPU"之间反复横跳。

**3. 别用平均分判断改动好坏**
平均分会掩盖灾难。看单题、看最差的那几道、看前三段加权。

**4. 召回不能砍，喂料可以减**
`top_k` 是网，`k_reranker` 是给模型看几份。砍网会让正确答案进不了池子。

**5. 分数异常低时，先查服务活着没**
`docker inspect --format '{{.RestartCount}}'`。我那 100 次重启，一开始被当成检索问题查了半天。

**6. 改文档比改代码划算**
同样解决同义词问题，改 4 篇文档 = 开一路 LLM 改写的 6 倍效果，且零副作用。

## 最后一句

这套系统现在跑得不错，但让我最有收获的不是"跑通了"，是那些**被数据推翻的判断**：

- 以为砍候选池没影响 → 一道题崩了
- 以为改写能救同义词 → 它引入的污染比解决的问题多
- 以为 50 题 94% 挺好 → 换个说法就掉一半
- 以为相关度低是检索问题 → 是重排崩溃了 100 次

**每一个"以为"背后，都是一次没做测量就下的结论。**

如果你也在本地折腾 RAG，建议第一件事不是调参，是建一个自己的测试集——哪怕只有 30 道题。有了它，你才知道自己每次改动到底是进步，还是"感觉上进步"。
