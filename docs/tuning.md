# 调参手册

给「改了什么、会影响什么、怎么验证」的一份对照表。

**前提**：你已经能跑通评估（见 [部署说明](deploy.md) 和 [README 的快速开始](../README.md#快速开始)）。

---

## 一、一个提问经过哪几层

调参前先知道参数落在哪，否则会改错地方。

```
你的问题
   │
   ├─① 向量化        embedding_model
   │
   ├─② 粗召回        top_k            ← 捞出候选池
   │
   ├─③ 重排          top_k_reranker   ← 从池子里挑几段送模型
   │                  external_reranker_url
   │
   ├─④ 过滤          relevance_threshold  ← 太不相关的丢掉
   │
   ├─⑤ 拼 prompt     chunk_size 决定的块长
   │
   └─⑥ 生成          temperature / top_p / top_k（生成层）
                      num_ctx
```

**关键分界线**：①—⑤ 是**检索层**，本仓库的评估脚本测的就是这一段；⑥ 是**生成层**，评估测不到。

---

## 二、每个参数管什么

### 检索层（评估能验证）

| 参数 | 本仓库值 | 调大会怎样 | 调小会怎样 |
|---|---|---|---|
| `rag.top_k` | 12 | 候选池更大，召回率高，重排变慢 | **危险**：正确答案可能进不了池子 |
| `rag.top_k_reranker` | 4 | 模型看到更多资料，prompt 变长 | 可能漏掉答案所在的段 |
| `rag.relevance_threshold` | 0.15 | 更严格，容易把正确资料也滤掉 | 更宽松，寒暄也会带上资料 |
| `rag.chunk_size` | 500 | 块更完整，但检索精度下降 | 块更聚焦，但答案可能被切开 |
| `rag.chunk_overlap` | 50 | 跨块的答案更容易被拼上 | 边界处的答案容易丢 |
| `rag.enable_hybrid_search` | 开 | — | 关掉只剩向量检索，中文术语命中会掉 |
| `rag.embedding_model` | `bge-m3-cpu` | — | — |

### 重排服务（在容器里，不在参数面板）

| 参数 | 本仓库值 | 说明 |
|---|---|---|
| `DOC_CHARS` | 500 | 送给重排模型的单块字符数。**低于 400 会把答案步骤切掉**，正确块掉到第 3 名 |
| `BATCH` | 8 | 一次送几条，超过 TEI 的 `max-client-batch-size` 会 422 |

### 生成层（评估测不到，只能人工抽检）

| 参数 | 本仓库值 | 说明 |
|---|---|---|
| `temperature` | 0.2 | 只影响措辞抖动，对 RAG 准确率几乎无收益 |
| `top_p` | 0.75 | 按累计概率截断 |
| `top_k`（采样） | 20 | 按排名截断，和 top_p 同时生效取交集 |
| `num_ctx` | 8192 | 由显存决定，不是想开多大就开多大 |

## 三、三个「改了要重来」的参数

这几个不是调，是**重建**——改了必须重新处理所有文档，几十分钟起步：

| 参数 | 为什么 |
|---|---|
| `chunk_size` | 所有文档要重新切块、重新向量化 |
| `chunk_overlap` | 同上 |
| `embedding_model` | 向量维度可能变，旧向量全部作废 |

**建议**：这三个在你第一次建库时就定好。真要改，预留半天。

## 四、调参流程（六步）

```bash
# ① 先有基线（没基线别开始）
cd eval
python run_eval.py --run --tag 基线

# ② 只改一个参数（改完必须重启+确认）
docker exec open-webui python -c "…改 config 表…"
docker restart open-webui
python snapshot.py          # 确认真的变了

# ③ 再跑一轮
python run_eval.py --run --tag kr6

# ④ 看对比
python report.py --open

# ⑤ 判断：涨了保留 / 跌了回滚 / 没变就别在上面花时间

# ⑥ 回滚（如果需要）
docker restart open-webui   # 改回原值后
```

**六步里最容易跳过的两步，恰好决定结论是否可信**：改完不重启 → 测的是旧参数；不打 tag → 一周后分不清哪轮是哪轮。

## 五、本仓库的实测结论

全部来自 70 题评估集，可复现。

| 改动 | 结果 | 结论 |
|---|---|---|
| `top_k` 12 → 6 | 单题 w3 从 0.72 崩到 **0.25**，整体下跌 | **候选池不能砍**，砍了正确答案进不来 |
| `top_k_reranker` 6 → 4 | 命中率 +0.9 点 | **判定为噪声**，保留的理由是省 token |
| 查询改写 开 → 关 | top1 0.749 → **0.833**，召回段数 8.3 → 3.3 | 改写引入模型自身知识（Windows 污染），得不偿失 |
| 阈值 0.15 | 挡住寒暄类提问不带资料 | 别设太高，会把正确资料一起滤掉 |
| 改 4 篇文档（加别名） | 命中率 **+7.1 点**，同义变体 50% → 100% | **改文档比改参数划算 6 倍** |

最后一条是全部结论里最重要的：

> **调了两周参数涨 4 个点，改 4 篇文档涨 7 个点。**
> 而且改文档零副作用，调参数经常会按下葫芦起了瓢。

## 六、怎么判断「涨了」是真的

**小样本会骗人。**

同样是改 `top_k_reranker`，只看 2 道题时是「涨了」，看到 6 道题时结论反转。

判断涨跌是否真实，看三个东西：

| 看什么 | 在哪 | 说明 |
|---|---|---|
| **单题变化** | 报告里的散点图 | 涨的那几个点是真命中，还是陪跑段碰巧带上了关键词 |
| **剔除 flaky 后的口径** | 报告 KPI 第三张卡 | 题库里有几道题本身在阈值附近抖动，会污染对比 |
| **分类是否同向变化** | 分类双条 | 只有一类涨、其他类跌，往往是运气 |

**经验阈值**：总分变化 < 1 个点，当作噪声，不要写进结论。

## 七、五个常见误区

**① 一次改五个参数**
涨了不知道是谁的功劳，跌了不知道是谁的锅。**一次一个。**

**② 用平均分判断好坏**
平均分会掩盖灾难。一道题从 0.9 崩到 0.1，另外九道各涨 0.01，平均分还涨了。

**③ 改了参数没重启**
有些参数启动时读一次，不重启等于没改。改完用 `snapshot.py` 确认。

**④ 不做记录**
三个月后看到「91.2%」，不知道当时是什么配置。**每轮自动存 `.meta.json` 就是为这个**。

**⑤ 只盯着总分**
总分 90% 里可能有 15 道「无答案」题全是蒙对的。**看分类，找最弱的那一类。**

## 八、该从哪开始

如果你刚建好库，不知道从哪下手：

```
1. 跑一轮基线
2. 看分类命中率，找最低的那一类
3. 打开那类的几道错题，看召回的资料对不对
   ├─ 资料没捞到   → 文档问题（加别名、改标题）或 top_k 太小
   ├─ 捞到了但没答对 → 重排/阈值问题，或生成层问题
   └─ 库里根本没有   → 补文档
4. 从「文档问题」开始改，不要先动参数
```

**最后一条是这套方法最反直觉、也最省时间的地方。**
